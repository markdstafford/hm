# ADR 005: Event-sourced history + daily snapshots

## Status

Accepted

## Context

`hm` needs to answer time-travel questions: "why are we off track on this quarter's objective?", "how has the roadmap drifted day-by-day?", "what events led to this status change?". We need a data model that makes these queries fast and reliable, without locking us into a specific storage engine.

Constraints:

- Time-travel is needed back ~6 months, max 1 year
- Day-level granularity is sufficient — intra-day rewind is not a requirement
- Storage is SQLite (ADR-004), which has no native time-travel
- Source systems already retain change history; `hm` can re-ingest if needed

## Decision

For every entity with a meaningful lifecycle — issues, PRs, roadmap items, objectives, key results — `hm` stores three things:

1. A **primary table** with current state
2. An **events** table capturing every meaningful change (status transitions, assignments, reviews, priority changes, scope changes) with timestamp and actor
3. A daily **snapshot** table containing one row per (entity, day) with materialized state for that day

Snapshots are generated by a background job. If `hm` is closed for several days, missing snapshots are reconstructed from events + source-system data on next ingestion.

Status reports are stored as one immutable row per (team, week) — a degenerate form of the same snapshot pattern, where the snapshot is the report itself.

## Consequences

**Positive:**
- "Show me status on day D" is a direct row lookup — instant
- "What changed leading up to this transition" is a focused events query
- Snapshots are recomputable from upstream history, so they act as a cache, not a record
- Pattern works in any OLTP store; no engine lock-in
- Retention is explicit: keep daily snapshots for ~1 year; compact to weekly beyond if needed

**Negative:**
- More tables than a simpler model — roughly three per entity type
- Daily snapshot job has to run reliably (mitigated by replay-from-events)
- Storage overhead vs. storing only current state (negligible at this scale)
- Adding a new entity type means adding its events + snapshot tables

## Alternatives considered

### Option 1: Pure events, no snapshots

Store only events; reconstruct point-in-time state by folding events on every query.

**Pros:**
- Minimal storage
- Single source of truth — no cache invalidation concerns

**Cons:**
- "Status on day D" requires folding all events up to D — slow for many entities across many days
- Aggregate metrics ("PRs backing up over time") require expensive recomputation
- UI latency degrades as history grows

**Why not chosen:** Trading storage for query speed is the right trade at this scale. Snapshots are tiny — a few thousand rows per year of history — and they make the user-facing queries instant.

### Option 2: Storage-layer versioning (LanceDB-style)

Let the storage engine version each row on every write; query "as of version X".

**Pros:**
- No explicit snapshot modeling
- Versioning is automatic

**Cons:**
- Versions align to writes, not to days — we'd still need day-aligned queries on top
- Locks us into a storage engine that supports this (LanceDB)
- Versions and the UI's "end-of-day state" don't naturally line up

**Why not chosen:** Even with native versioning, we'd build a day-aligned view on top — the same shape we're building in SQLite. The "free" versioning isn't free for our use case.
